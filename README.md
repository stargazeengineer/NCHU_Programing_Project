# NCHU_Programing_Project
這是一份計算機程式設計期末專題 >&lt;

## 摘要

本研究針對多日旅遊行程排程問題，以既有之 C++ 貪婪演算法以及 DFS 算法加剪枝為基礎，探討兩者演算法在各項鰾線上何者更適合應用在旅遊行程排程問題。並且研究過程中逐步將原始二維網格曼哈頓距離模型演進為「以景點為節點、以實際公里數為邊權重、並支援去回程非對稱路徑」的有向帶權圖模型，進一步加入矩陣輸出檢視、使用者互動式客製化設定，以及景點資料庫擴充（由 9 個擴充至 28 個景點）。在系統實作與迭代過程中，針對距離語意定義、去回程路線差異、預算與使用者客製化以及大規模景點資料維護等問題提出相應解法，最終完成系統的建置。

關鍵詞： 行程規劃、貪婪演算法、DFS 剪枝、有向帶權圖、距離矩陣、客製化排程

### 一、 緒論與系統基準

#### 1.1 問題背景

多日旅遊行程規劃需在有限天數與每日營運時段內，考量景點開放與關閉時間、停留時長、不同時段人潮程度以及移動距離對整體成本的影響。原始系統採用貪婪策略，在每日起點與初始時間下，逐輪評估尚未排入之候選景點是否可於時段內抵達並完成停留，並以成本公式 $\text{Cost} = \text{Crowd} + \text{Dist} \times W_{\text{dist}}$ 挑選單步成本最低的景點。針對不同情境，我們想探討貪婪演算法與 DFS 剪枝演算法何者更適用於這樣的情境。

#### 1.2 實作目標

本實作歷程旨在維持原有貪婪排程狀態轉移、時間窗檢核（tryVisit）與成本計算核心不變的前提下，完成以下階段性改進：提升兩地距離估算的準確度，改以有權重圖建模。符合純 ASCII／英數程式碼規範，避免原始碼、註解與輸出字串出現中文字元。將距離權重語意明確化為「景點間距離」，並支援實際公里數與去回程路線差異。提供有向距離矩陣輸出功能，便於驗證與除錯。導入使用者客製化參數（天數、起點、預算上限、想去的景點集合），並擴充可選景點數量。

### 二、 系統實作歷程

#### 2.1 第一階段：

網格有權重圖與最短路徑查詢初期將 20 x 20 網格節點建構為帶權圖（adj），依據市中心與外圍區域設定基礎通行權重，並針對特定相鄰路段微調權重，再透過 DFS 演算法求得起點至各節點的最短路徑距離，同時加入起點距離快取機制（prepareFromPos）以降低重複計算成本。

#### 2.2 第二階段：

景點間有向公里距離矩陣建置為使權重直接反映兩地距離而非網格逐格行走之累積權重，系統改以景點索引建立有向距離矩陣 distKmGraph[from][to]，並將單位轉換為實際公里數（double）：距離與時間／成本銜接：以 MIN_PER_KM 換算移動分鐘數，以 DIST_WEIGHT 計算距離成本，保留原有 crowd 與 cost 組合邏輯。去程與回程差異建模：透過 setSpotDistKm(fromIdx, toIdx, km) 分別設定起點至終點與終點至起點的公里數；當去回程走相同道路時數值相近或相同，當走不同道路、單行道或替代動線時則設定不同公里數。近似距離遞補：針對尚未逐一指定或起點不在景點座標上的情況，以 calcApproxKm 產生合理近似公里數作為備援，避免缺漏。

#### 2.3 第三階段：

有向距離矩陣視覺化輸出為利於人工檢核各景點對之間的距離設定是否合理，實作 printDistKmGraph()，先印出節點索引與景點名稱／ID 對照表，再以對齊欄位印出完整的 From\To 有向距離矩陣（單位 km，保留一位小數）。

#### 2.4 第四階段：

使用者客製化與景點庫擴充為提升實際應用彈性，新增 UserConfig 結構與 configureFromUser() 互動流程，支援使用者自訂：旅遊天數（days）出發起點座標（startX, startY）總成本預算上限（maxBudget，於 runGreedy 挑選候選景點時檢核 totCost + cost 是否超出上限）欲造訪之景點清單（wantIds）同時於 initDefaultSpots() 逐步擴充景點資料庫，由最初 9 個景點擴增至 18 個，再進一步擴充至 28 個景點（涵蓋市區商圈、文化場館、夜市、山線與海線景點），並同步補齊對應的公里距離設定。實作階段核心調整內容保留之既有邏輯網格帶權圖階段20x20 網格建圖、Dijkstra 最短路徑與快取貪婪選點、時間窗與成本公式字元規範階段移除程式碼內所有中文字元（註解與輸出全英文）整體排程流程與資料結構公里有向圖階段distKmGraph[from][to] 公里權重、去回程獨立設定tryVisit 時間推算與 cost 計算矩陣輸出階段printDistKmGraph() 印出索引對照與完整矩陣既有距離查詢與排程結果輸出客製化與擴充階段天數、起點、預算上限、自選景點與 28 個景點資料每日重置起點與時間、貪婪最佳化

### 三、 實作過程中所遇問題與解決方案

#### 3.1 問題一：二維網格曼哈頓距離與真實道路路況之模型落差問題描述

系統原型階段採用 $10 \times 10$（後擴增為 $20 \times 20$）二維網格地圖，並以曼哈頓距離 $\vert{}x_1 - x_2\vert{} + \vert{}y_1 - y_2\vert{}$ 搭配固定每格移動時間估算兩地交通成本。然而，此模型假設都市道路完全呈均勻方格分布且各路段通行代價相同，無法反映臺中市跨區（如城區往返海線高美濕地或山線谷關、新社）之實際路網結構、山路繞行與尖峰路況差異。經過我們組員兼討論，我們原本想導入 Dijkstra 最短路徑演算法搭配起點距離快取機制（prepareFromPos），使各區域具備差異化通行權重，但後來認為將我們的地圖改為有權重的圖就能在更簡單的想法下有效解決曼哈頓距離計算時不准卻的問題，使模型兼具真實距離精度與原有排程邏輯之一致性。

##### 什麼是有權重的地圖? 如何提高其距離計算的準確性及真實性?

原本的程式把地圖當成無權重網格（如下圖），只用座標差算曼哈頓距離，假設每一格的移動成本都相同，而且去程與回程距離永遠一樣。為了提高準確性與真實性，我們先嘗試替不同區域與路段加上權重並用最短路徑計算，接著改為以「景點」為節點建立有向距離矩陣，直接用實際公里數作為權重。

#### 3.2 問題二：景點資料來源繁雜與時段人潮量化困難問題描述

臺中市政府觀光旅遊網收錄多達 449 項景點資料，但各景點營業時間格式不一（如固定整點、依各店家而定或分平假日與夏冬令），且公開頁面並未提供早、中、晚三時段之量化人潮指數與網格座標，若全數直接納入搜尋亦將導致組合空間過大、難以驗證演算法行為。解決方案：建立結構化景點資料模型 Spot（包含座標、建議停留分鐘、開放與關閉小時及早／午／晚人潮指數）。初期先選取 9 至 12 個具代表性之景點作為精簡測試基準以驗證時間窗與排程邏輯；待核心穩定後，再依區域分布逐步擴充至 28 個景點（涵蓋城區、西屯／南屯／北屯、屯區、海線與山線），同時保留外部 CSV 匯入介面以利後續資料集擴展。  

#### 3.3 問題三：開發環境編譯異常與跨語言原型驗證需求問題描述

於 Visual Studio Code 進行 C++ 開發與測試期間，曾因本地編譯器環境異常而中斷功能驗證，若停滯於環境除錯將影響專題進度推進。解決方案：採用雙軌並行策略，先將資料結構與貪婪演算法原型轉譯為可於 VS Code 直接執行的 Python 版本以快速驗證時間推算與選點邏輯；待 C++ 編譯環境排除問題後，再以精簡、高可讀性的 C++ 結構重寫核心模組（如獨立出 tryVisit 單步試算函式），確保兩者邏輯完全對齊並維持 C++ 執行效能優勢。

#### 3.4 問題四：程式碼中文字元限制與跨環境亂碼風險問題描述

初期為便於理解演算法邏輯，於程式碼註解、測試字串與報表輸出中使用繁體中文，不僅在部分 Windows 終端機編碼下易產生亂碼，亦不符合專題對純 ASCII 程式碼之規範要求。解決方案：全面重構程式碼之文字資源，將所有函式註解、狀態提示與終端機輸出報表統一改寫為純英數與標準 ASCII 符號（例如以 Day 1 | 09:00-10:00 與英文景點代號呈現排程結果），確保原始碼在任何作業系統與編譯器設定下皆能無錯誤編譯並正常顯示。

#### 3.5 問題五：去程與回程路線非對稱之距離表示限制問題描述

在實際交通環境中，兩景點之間往返可能行經相同幹道，亦可能因單行道、高架交流道匝道或替代動線導致去程與回程公里數不同；若採用傳統無向對稱距離矩陣，將無法精確表達方向性差異。解決方案：設計有向二維距離矩陣 distKmGraph[from][to] 與設定介面 setSpotDistKm(fromIdx, toIdx, km)，允許針對 from -> to 與 to -> from 分別設定相同或相異之實際公里數，兼顧一般雙向道路之設定便利性與特殊動線之方向精確度。

#### 3.6 問題六：客製化預算上限與候選景點合法性之狀態一致性問題描述

在加入使用者互動設定（UserConfig 與 configureFromUser()）以支援自訂旅遊天數、出發座標、總預算上限（maxBudget）與欲造訪景點清單（wantIds）後，若使用者輸入無效景點 ID，或某候選景點雖符合時間窗但會使累計成本超出預算，可能導致陣列越界或錯誤更新多日排程狀態。解決方案：在建立候選索引列表 candIdx 前先執行 ID 合法性過濾；於 runGreedy 內層逐輪搜尋時，採「雙重條件檢核」機制——先透過 tryVisit 確認抵達時間、等待開門與離開時間皆符合營業時段與當日上限，再檢核 totCost + cost <= maxBudget，僅在兩者同時成立時才納入最佳候選比較與狀態轉移。

#### 3.7 問題七：景點規模擴充後之距離矩陣維護與檢核可讀性問題描述

當景點數量由初期 9 個逐步擴充至 18 個再增至 28 個時，有向邊總數達 $28 \times 27 = 756$ 組；若全數依賴人工逐筆輸入極易遺漏或出錯，且直接輸出 $28 \times 28$ 數值矩陣時若缺乏索引對照，將難以人工判讀各列與各欄對應之景點。解決方案：導入「近似距離預設＋顯式邊覆蓋」機制，先由 calcApproxKm 為所有景點對填入合理基礎公里數，並以 hasExplicitEdge 追蹤已精確校準之路段，再針對跨區與主要幹道呼叫 setSpotDistKm 進行覆蓋；同時實作 printDistKmGraph() 視覺化檢核功能，先輸出 [index] name (ID:...) 對照表，再以對齊欄位印出 S0..S27 完整有向距離矩陣以利驗證與除錯。

#### 3.8 問題八：貪婪演算法之局部最佳限制與專題延伸方向釐清問題描述

貪婪策略（runGreedy）在每一決策輪次僅挑選當下單步成本最低的可行景點，雖具備極快運算速度與直覺邏輯，但可能因前期選擇近距離低人潮景點，導致後續熱門景點被迫排入尖峰時段或因時間不足而遺漏，呈現「局部最佳不等於全域最佳」之特性。解決方案：將貪婪演算法定位為系統高效能基準線（Baseline），在確保時間窗與預算約束下快速產出穩定可行解；同時在系統架構中保留完整狀態評估介面（tryVisit 與成本公式），作為後續擴充「深度優先搜尋結合時間窗回溯剪枝與分支限界（DFS + Branch and Bound）」或局部搜尋策略之直接對照組，以利量化比較不同演算法在總成本、人潮避開效益與執行時間上之權衡。


#### 3.9 問題一：權重語意與使用者期望不一致問題描述

初期以網格鄰居邊權重搭配 Dijkstra 求最短路，雖能反映區域路況，但與使用者期望「一個景點到其餘每個景點的權重直接代表兩地距離」之直覺模型有所差異。解決方案：將圖模型調整為以景點為節點的兩兩有向距離矩陣 distKmGraph[i][j]，使任一景點到其他景點的權重直接代表兩地距離，並保留起點不在景點時的近似距離備援機制。

#### 3.10 問題二：程式碼中出現中文字元限制問題描述

開發與討論過程中曾使用中文註解與中文輸出文字，不符合「程式碼內不可有中文字元」的要求。解決方案：在後續所有程式碼版本中，統一將註解、提示字串與報表輸出改為純英數與 ASCII 符號，並於每次修改時維持此規範。

#### 3.11 問題三：去程與回程路線可能不同之距離表示問題描述

實際道路環境中，兩地往返可能行經相同幹道，也可能因單行道、交流道或替代路線導致去程與回程距離不同；若僅使用無向對稱距離，將無法表達此差異。解決方案：採用有向矩陣 distKmGraph[from][to] 與 setSpotDistKm(fromIdx, toIdx, km)，允許針對不同方向填入相近或相異的公里數，兼顧一般往返的簡潔性與不同路線的差異性。

#### 3.12 問題四：客製化預算限制與候選景點篩選之狀態一致性問題描述

加入使用者自訂天數、起點、預算上限與想去的景點後，需避免無效景點 ID 造成錯誤，且須確保超過預算的候選景點不會被錯誤納入排程或破壞多日迴圈狀態。解決方案：在建立 candIdx 時過濾不存在的景點 ID；在 runGreedy 內層候選評估時，先以 tryVisit 確認時間可行性，再檢查累計成本加上單步成本是否超過 maxBudget，僅在合法條件下更新最佳候選與累計狀態。

#### 3.13 問題五：景點數量擴充後的矩陣維護與可讀性問題描述

當景點數由 9 個擴增至 18 個再至 28 個時，若逐一人工填寫全部 $28 \times 27 = 756$ 組有向距離將過於繁瑣，且矩陣印出若缺乏索引說明容易混淆。解決方案：先以 calcApproxKm 填入基礎公里數並搭配 hasExplicitEdge 追蹤明確設定之邊，再針對主要與跨區／去回程路段呼叫 setSpotDistKm 覆蓋；輸出時則先印出 [index] name (ID:...) 對照表，再印出 S0..S27 矩陣以利判讀。

### 四、 結論與未來展望

本系統在不更動核心貪婪排程與時間窗檢核邏輯的前提下，成功完成了從網格最短路到景點間有向公里距離矩陣的轉換，並整合了矩陣輸出、使用者客製化參數設定與 28 個景點資料。後續若需進一步提升規劃品質，可朝「依時段動態調整公里或通行時間權重」、「針對自選景點提供更強的覆蓋率或最佳化搜尋策略（如局部搜尋或動態規劃）」以及「將景點與距離資料外部化為檔案讀取」等方向持續擴充。
